
# ADR-001: Mantener capas simples para persistencia y conservar Observer para notificaciones

## Estado
Aceptado — 13 de noviembre de 2026

## Contexto

El sistema de reembolsos utiliza una arquitectura en capas simples.
El servicio SolicitudReembolsoService depende directamente de
RepositorioSolicitudesJpa.

Actualmente no existe un plan confirmado para cambiar el motor
de base de datos. Por otra parte, Contabilidad tiene prevista una
integración externa para el proceso de pagos.

## Alternativas consideradas

1. Mantener la arquitectura en capas simples.
2. Migrar toda la persistencia a arquitectura Hexagonal.
3. Crear puertos e interfaces adicionales para persistencia y notificaciones.

## Decisión

Se mantiene la arquitectura en capas simples para la persistencia.
No se agrega una interfaz de puerto porque actualmente no existe
una necesidad real de cambiar el motor de base de datos.

Para las notificaciones se conserva la interfaz
ObservadorCambioEstado, porque permite que NotificadorContabilidad
cambie su implementación interna para conectarse con un sistema
externo sin modificar el servicio ni los otros observadores.

## Consecuencias positivas

- Se evita agregar abstracciones que no son necesarias actualmente.
- Se conserva una estructura sencilla de mantener.
- La notificación ya tiene un punto de extensión para futuras integraciones.

## Consecuencias negativas

- Si en el futuro se cambia el motor de base de datos, será necesario
  introducir una interfaz de persistencia.
- La arquitectura no tiene el mismo nivel de desacoplamiento
  para todas las dependencias externas.

## Principios aplicados

Se aplica YAGNI, porque no se construyen abstracciones para
necesidades que todavía no existen.
